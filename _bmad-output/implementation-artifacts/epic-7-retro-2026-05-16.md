## What Did Not Go Well

### 1. 🚨 E7-F1 — Completion does not persist across force-stop/relaunch

Discovered during on-device verification on Samsung A520F (2026-05-16). After completing 3/3 sessions on the Today screen, force-stopping the app, and relaunching, the completion ring resets to 0/3 and completed cards disappear. Root cause: `TodaySessionCubit` is in-memory by design, and the `daily_plans` table only carries a single plan-level `isCompleted` boolean (no per-session column). Real fix requires an Epic 8 SessionLog DAO.

**Impact:** Visible UX regression for alpha users who close the app mid-day. Acceptable in alpha (per Paolo); **not acceptable past beta**. Ledger entry E7-F1 already filed with screenshots in `/private/tmp/`.

**Lesson:** Story-creation should explicitly mark in-memory state with persistence implications and link forward to the story that closes the gap. Story 7.3 dev notes mention "Epic 8 replaces this stub" but did not register it as a tracked deferred item — it surfaced via on-device verification, not via process.

### 2. Story 7.3 — Positional vs identity completion bug caught in code review, not story-creation

Code review of 7.3 surfaced two `Decision-needed` items: after `swapHero(2) + markSessionCompleted`, sessions 0 and 1 are visually marked "completed" though never executed, and the actually-completed session 2 disappears. The fix was applied in-cycle, but the root cause is a product-semantics gap (completion-by-position vs completion-by-identity) that should have been resolved during story-creation.

**Lesson:** Stories that introduce a Cubit/BLoC with state derived from collection indices need a pre-flight architect check on identity-vs-position semantics. Add to story-creation checklist for Epic 8+.

### 3. Hero tag collision in Story 7.3 — found by Story 7.4 review

Story 7.3 used `'session-hero-${sessionType}'` as the Hero tag. During the 300ms `AnimatedSwitcher` cross-fade, two `HeroSessionCard` instances are mounted simultaneously; if both share the same `sessionType`, Flutter throws "multiple heroes share the same tag". Story 7.4's code review flagged it; patch applied retroactively to 7.3 code (`-$heroIndex` suffix). Story 7.3's own review missed this.

**Lesson:** When wrapping a widget with `AnimatedSwitcher` *and* `Hero`, the cross-fade window is a code-review checklist item. Add to the Edge Case Hunter prompt template.

### 4. i18n hardcoded across 5+ files — debt growing across stories

Italian copy hardcoded in `today_page.dart`, `completion_ring.dart`, `completed_session_card.dart`, `state_indicator.dart`, `session_card_helpers.dart`, `hero_session_card.dart`. The "COMING UP" header remained in English. ARB file exists but `gen_l10n` is not wired. Three Story 7.x reviews explicitly deferred i18n; debt is now visible enough to refactor cost.

**Decision (Paolo, in retro):** Promote to dedicated **Epic 7.5 interstitial** before Epic 8 — same pattern as Foundation Hardening 6.5.

### 5. AC2 (above-the-fold on standard phone) — not testable

Story 7.3 AC2 requires "no scroll required to see the primary action" on a standard phone. No golden / viewport test infrastructure exists. The AC was verified only by inspection. Deferred — recommend coupling to Epic 11 (Responsive Layout) where the infra has natural rationale.

### 6. `_isSamePlan` heuristic is fragile (Story 7.3 deferred item)

Comparing `generatedAt` timestamp + `sessions.length` to detect "is this the same plan" can miss a regenerated plan with identical timestamp + length. `TodaySessionCubit` would then keep stale completion state. Low probability today, becomes higher when Epic 8 wires real session navigation that may regenerate fast.

**Resolution path:** Roll into Story 8.0 (SessionLog) refactor — switch to a stable plan ID derived from DB row id rather than timestamp+length heuristic.

### 7. Drift "many small deferrals" — high volume of deferred review items

Counts: 7.2 = 14 deferred (mostly explicit "spec-driven" or "Story 7.3 scope"), 7.3 = 3, 7.4 = 2. All well-argued and each entry cites the future story that resolves it. But the absolute volume warrants vigilance — the Deferred Items Budget caps the *open* count, not the per-story growth.

**Lesson:** When a story produces > 10 deferred items, that itself is a signal worth reviewing in the next retro — even if the budget is not breached.

## Key Insights

1. **Scheduled product sessions resolve carry-over slippage.** Three epics of slippage on E5-T2/T4 closed when the team scheduled and executed dated decision sessions instead of deferring to "next sprint planning".
2. **Sprint binding with explicit rollback rules works.** Story 7.1b's "Binding: must merge same PR cluster, otherwise Rule 1 removed before 7.1 merge" is the template for inter-story coupling.
3. **Cubits with state derived from collection indices need pre-flight identity-vs-position review.** Story 7.3 caught the bug in code review; cheaper to catch in story-creation.
4. **i18n debt compounds quickly when each story adds Italian-as-strings.** Three deferrals across 7.x is the threshold for a dedicated migration story.
5. **On-device verification is irreplaceable.** E7-F1 was invisible to the test suite (which exercises in-memory cubit state, not full app lifecycle). The CLAUDE.md "On-Device UI Verification Protocol" earned its keep.
6. **High deferred-item volume per story is a signal even within budget.** Story 7.2's 14 deferrals are all argued, but the volume itself warrants attention.
