# Story 21.5: Shared-Session Scoring — Live Deployment & Two-Device End-to-End Verification

Status: review

## Story

As the project team closing out v2,
I want the shared-session scoring server path (`score_shared_session` Edge Function + `pg_cron` sweep) deployed live and exercised end-to-end on two real devices,
So that the one concrete unverified path at v2 close (E21R-1) is proven working in production conditions, not just at the unit/SQL layer.

## Context

**Epic 21 — Leaderboard & Scoring (v2.5), backlog follow-up surfaced by the Epic 21 retrospective GUI gate (2026-07-05, action item `E21R-1`, epics.md:2855-2861).** `epic-21: done` already — this story is an explicit exception opened by the retro, not a re-open of the epic's other stories. Epic 21 shipped the full points/leaderboard/bonus/sweep system (21.0–21.4), and its two-device gate (`epic-verification-history.md`, "Epic 21... 2026-07-05: PASS") verified the **client-facing** leaderboard surface live. What it explicitly did **not** verify:

1. **The `score_shared_session` Edge Function was never deployed** — its deploy was "blocked by the harness (production-deploy guard)" during the Epic 21 gate session. Its logic is covered only by `supabase/functions/score_shared_session/index_test.ts` (Deno unit tests) — never invoked against a real Supabase project by a real client call.
2. **The `pg_cron` sweep (`sweep_unscored_shared_sessions`, migration `0014`) was applied to the live project's schema but its *scheduled execution* was never confirmed** — `pg_cron` is the repo's first `CREATE EXTENSION` and first `service_role` grant (0013/0014), and "jobs run in pg_cron's home database" is a documented deploy caveat from Story 21.4's review that was never checked against the real project.
3. **The rank-freeze *release* half (Story 21.2-AC3) was not re-tested on-device** — the Epic 21 gate proved the freeze *holds* (pinned paolo at 4° after boosting his points to the top total), but returning to `Active`/`Fatigued` to *release* the pin was skipped at the gate to avoid on-device drift-DB surgery (API 26 device has no on-device `sqlite3`). It is covered by `LeaderboardBloc`'s `_freezeStore.clear()` unit tests only.

**This story is deploy-and-verify, not new feature work.** No new Dart or SQL logic is expected — everything to be exercised (`score_shared_session/index.ts`, `award_shared_session_points`, `sweep_unscored_shared_sessions`, `LeaderboardBloc`'s freeze/release logic) already shipped in Stories 21.0–21.4 and is fully covered by existing unit/pgTAP tests. The gap this story closes is purely "has this ever run against a live deployment," which by definition cannot be closed by writing more unit tests — it requires an actual `supabase functions deploy`, live `pg_cron` execution, and a live two-device session.

Given two devices (reusing the Epic 20/21 gate rig or equivalent: one physical + one AVD/emulator, both signed in as accepted friends, both Pro) complete a co-located shared session together and **both** submit RPE

**AC3 — Drop-out path is scored by the live `pg_cron` sweep, not the client path:**
Given a second co-located shared session where one participant submits RPE and the other force-quits/goes offline before submitting (the drop-out case), and at least 30 minutes elapse (the sweep's grace window)
When the `pg_cron` schedule fires `sweep_unscored_shared_sessions()` on its live 5-minute cadence
Then `cron.job_run_details` (or equivalent Postgres introspection) shows a successful run of `sweep-shared-session-scoring` after the grace window, the submitting participant's Classifica total increases by their `base_points × 1.5` after the sweep runs, and the never-submitted participant receives no new `leaderboard_entries` row — confirming both "pg_cron actually executes on this project" and "jobs run in pg_cron's home database" (the Story 21.4 deferred deploy caveat) hold true live.

**AC4 — Rank-freeze release is confirmed on a real device:**
Given a device whose user is in a protective state (`AtRisk`/`Recovering`) with a frozen Classifica rank (reproducing the Epic 21 gate's frozen-at-4° scenario)

Then the Classifica shows the user's live (unfrozen) rank, not the previously-pinned one — closing the "release-half not re-tested on device" gap (epic-21-retro-2026-07-05.md:42).

**AC5 — Zero regressions, no unintended production-data residue:**
Given all live verification steps above are complete
When `flutter analyze lib/ test/` and `flutter test` are run from `pulse_coach/`
Then the pre-existing suite continues to pass at the Story 21.4 baseline (1315 passed, 1 skipped) with zero new failures (this story is deploy/verification-only — no Dart/SQL changes are expected unless a live defect is found and explicitly logged); AND any fixture data seeded for the two live sessions (test sessions, `leaderboard_entries` rows, `shared_sessions`/`session_participants` rows) is either the real outcome to be kept, or is cleaned up afterward with the before/after state documented in this story's Dev Notes — mirroring the "all fixtures deleted at the end → backend restored to as-found" discipline from the Epic 21 gate record.

## Dev Notes

### This Is a Deploy-and-Verify Story, Not a Feature Story

Unlike Stories 21.0–21.4, this story's "implementation" is operational: deploying an already-shipped Edge Function, confirming an already-scheduled `pg_cron` job actually runs, and driving already-built UI on two real devices. Resist the urge to write new Dart/SQL code to "make this easier to test" — the whole point of this story is proving the existing, already-tested code path works live. If a live defect is found, it becomes a `[Review]` finding for a human decision (fix now vs. defer), consistent with how Stories 21.1–21.4 treated review findings — not a silent in-story patch.

### Safety Guard Around the Edge Function Deploy

The Epic 21 gate's Edge Function deploy was blocked by "the harness (production-deploy guard)" — this is a deliberate safety control, not a bug to route around. If Task 2 hits the same guard, the correct action is to surface it to Paolo for a decision on the intended deploy mechanism (CLI from a different shell, dashboard-triggered deploy, etc.), not to find a way to bypass the guard from within this session.

### Reuse the Two-Peer Smoke Test's Rig, Not a Fresh Setup

`pulse_coach/test/integration/shared_session_two_peer_smoke_test.dart` already has a working two-seed-user, real-Supabase-Realtime-channel setup (E19R-1). Read it before improvising a new two-device configuration — it may already document the exact seed users, project, and connection pattern this story's live session needs, saving significant setup time and avoiding a second, divergent test-account scheme.

### `E21R-B1` — Backup Before On-Device DB/Prefs Edits

New Category-B rule from the Epic 21 retro: whenever a gate step edits on-device `SharedPreferences`/drift DB, take a **verified backup of the file first**. At the Epic 21 gate, a `run-as cp` into `/data/local/tmp` was silently denied and produced an empty-file overwrite of `FlutterSharedPreferences.xml` (recovered, but `pro_upsell_dismissed_date` and `leaderboard_install_id` were lost). Staging must be shell→app only (`adb push` → `/data/local/tmp` → `run-as cp` **into** the app dir); the reverse direction (`run-as cp` **into** `/data/local/tmp`) is denied on this device and fails silently rather than erroring loudly — do not trust it without verifying the destination file's size/contents after the copy.

### Expected Values for Award Verification

`base_points = duration_minutes * intensity_weight` (intensity_weight: minimal/low=1.0, moderate=1.5, else=2.0 — mirrored across `ScoringConstants.intensityWeightFor` (Dart), `intensityWeightFor` (`index.ts`), and the SQL `CASE` in `sweep_unscored_shared_sessions`). Shared-session award = `round(round(base_points) * 1.5)`. Use these formulas to compute the exact expected point delta before/after each live session rather than eyeballing "it went up."

  **[Review][Decision] D2 — Shared-session host never receives shared-session award (`shared_session_remote_data_source.dart:25-47` vs `:87-108`)**
  - **Root cause:** `createSharedSession()` (called when a user taps "Shared Session" to host) inserts only into `shared_sessions` (`host_user_id`, `join_code`) — it never inserts a `session_participants` row for the host. Only `joinSharedSession()` (called by whoever enters the join code) upserts into `session_participants`. Confirmed by reading `shared_session_remote_data_source.dart` lines 25-47 and 87-108 directly. **Traced one level deeper into the actual failure mode:** `rpe_page.dart`'s RPE-submitted listener routes to `SubmitSharedSessionResultUseCase` for ANY participant (host or joiner) whenever `args.planId == null && args.sharedSessionId != null` — so the host's RPE *does* attempt the shared-result path, not the solo path. That call is `unawaited()` (rpe_page.dart:120-127) and invokes the `submit_shared_session_result` RPC (`0013_shared_session_scoring.sql:20-48`), which does `UPDATE session_participants ... WHERE session_id = ... AND user_id = auth.uid()` and explicitly `RAISE EXCEPTION 'not a participant of this session'` when `ROW_COUNT = 0`. Since the host has no `session_participants` row, this RPC call throws for the host on every single shared session, every time — silently, because the call site is `unawaited()`. This is a clean, precisely-diagnosed one-line-fix candidate (insert a `session_participants` row for `hostUserId` inside `createSharedSession()`, mirroring `joinSharedSession()`) — but is intentionally NOT patched here per this story's review-not-patch discipline.

Since the host is never a row in that table, a 2-person session (1 host + 1 joiner) only ever has **one** `session_participants` row. The moment that one joiner submits RPE, `allSubmitted` is trivially `true`, the session is scored, and `award_shared_session_points` runs for the joiner only. This reproduced identically on the very first live 2-device session ever run against production — it is not an edge case.
