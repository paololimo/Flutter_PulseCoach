## What Went Well

### 1. Spike Pre-Implementation — Validated Pattern

The Epic 3 health package spike (before Story 3.1) completed all platform configuration upfront:
- iOS: `NSHealthShareUsageDescription`, HealthKit entitlement
- Android: `READ_HEART_RATE`, `READ_STEPS`, `ACTIVITY_RECOGNITION`, Health Connect intent filter
- `health: ^13.3.1` and `sensors_plus: ^6.1.0` verified on pub.dev

**Result:** Task 0 in Story 3.1 was a simple verification — no code changes needed. Zero platform-related blockers across all 3 stories. Spike investment paid for itself by eliminating an entire category of risk.

**Lesson:** Spike before every new platform-specific library. Validated pattern — replicate for `geolocator` in Epic 4.

### 2. Boundary Design — `GetSensorContext` Anti-Corruption Layer

Story 3.3's `GetSensorContext` returns a plain `SensorContext` (not `Either`). This was the most important design decision of the epic:
- RPE-only mode (all-null `SensorContext`) is a first-class operational state, not an error
- Epic 5 `DailyPlanBloc` consumes `SensorContext` without knowing about `Either`, `SensorFailure`, HealthKit, or accelerometer internals
- Adding a new sensor in the future requires zero changes to Epic 5 code

**Lesson:** Boundary design with clean contracts between layers is what makes code maintainable long-term.

### 3. Failure Path Testing — Epic 2 Commitment Honored

All 3 stories included failure path tests before review:
- Story 3.1: permission denied, empty data, unknown exceptions
- Story 3.2: sensor unavailable, stream error, timeout
- Story 3.3: both sources fail (RPE-only), partial data, exception propagation

**Lesson:** The Epic 2 commitment to mandatory failure path testing was respected. Reviews still found edge cases, but the baseline was solid.

### 4. Epic Closure Workflow Respected

testarch-automate → testarch-traceability → retrospective → commit. No overlap with Epic 4 code. The fixed sequence (established as rule in Epic 2 retro) was followed.

### 5. Sonnet/Opus Review Workflow Confirmed

7 patches across 3 stories, 4 of which were crash-level or silent misbehavior:
- Story 3.2: Empty stream `StateError` (crash), no timeout (infinite hang)
- Story 3.3: No try-catch in `GetSensorContext` (crash, contract violated), NaN/Infinity misclassification (silent wrong result)

The review workflow continues to be the highest-ROI quality practice.

### 6. Concurrency Design in Story 3.3

Separate-await pattern for type safety over `Future.wait<dynamic>`:
```dart
final healthFuture = _getHealthData();
final activityFuture = _getActivityLevel();
final healthResult = await healthFuture;
final activityResult = await activityFuture;
```
Preserves concurrency while retaining static types. Mature pattern choice.

## What Didn't Go Well

### 1. Story Specs Missing Defensive Edge Cases — Systematic (3/3 Stories)

| Story | Review Finding | Crash-level? |
|---|---|---|
| 3.1 | `saveHealthData` result silently swallowed | No — data loss |
| 3.1 | Two separate `DateTime.now()` calls | No — timestamp drift |
| 3.2 | AC3 failure message mismatch | No — spec inconsistency |
| 3.2 | Empty stream `StateError` | **Yes** — crash |
| 3.2 | No timeout on stream consumption | **Yes** — infinite hang |
| 3.3 | No try-catch in `GetSensorContext` | **Yes** — crash |
| 3.3 | NaN/Infinity misclassification | **Yes** — silent wrong result |

**Root cause:** Story specs define ACs and failure paths but do not enumerate defensive edge cases (empty streams, timeouts, invalid inputs, unwrapped exceptions). The dev model follows the spec faithfully and does not add defensive code spontaneously.

**Action:** New section 'Defensive Requirements' in story template. SM compiles it during `bmad-create-story`. Focus: stream empty, timeout, invalid input, unwrapped exceptions from external packages. Not exhaustive — focus on crash-level and silent misbehavior.

### 2. DI/Testability Workarounds for External Packages

| Story | Package | Issue | Workaround |
|---|---|---|---|
| 3.1 | `health` | `Health()` is external singleton, no `@injectable` | `@module` abstract class in `HealthModule` |
| 3.1 | `drift` | `AppDatabase.behavioralStateDao` is `late final`, unmockable | Inject `BehavioralStateDao` directly, register via `HealthModule` |
| 3.2 | `sensors_plus` | `accelerometerEventStream()` is top-level function, not mockable | `typedef AccelerometerStreamFactory` + `.withOverride()` named constructor |
| 3.2 | `injectable` | Generator couldn't resolve function type as constructor param | Typedef workaround |

**Root cause:** External packages have constructors, singletons, and top-level functions that don't fit `@injectable` pattern. Each wrapper requires a unique testability workaround.

**Mitigation:** The `.withOverride()` pattern from Story 3.2 is now an established codebase precedent. Reusable for `Dio` and `geolocator` in Epic 4.

### 3. Deferred Items Growing — 28 Cumulative

From 13 (Epic 1) → 22 (Epic 2) → 28 (Epic 3). Rate: ~9 new items per epic. Most are low-priority, but some carry forward without finding a natural context:
- `getProfile()` caching — open since Epic 1 (3 epics)
- `saveHealthData` failure swallowed — deferred to Epic 5 (conscious decision)

**Action:** SM checks deferred item list during `bmad-create-story` and incorporates items where context is natural. No cleanup sprints — debt addressed in-context.

## Key Insights

1. **Spike before every new platform-specific library** — validated by health package spike eliminating all platform risk. Replicate for `geolocator` before Story 4.3.
2. **Story specs need 'Defensive Requirements' section** — 4/7 review patches were crash-level. Dev model follows spec faithfully; defensive edge cases must be explicit.
3. **Boundary design with clean contracts is the highest-value architectural decision** — `GetSensorContext` → `SensorContext` isolates Epic 5 from sensor complexity. Pattern to replicate at every layer boundary.
4. **Deferred items should be addressed in-context during create-story, not in cleanup sprints** — SM reviews deferred list and integrates where context is natural.
5. **Timeout and retry parameters must be concrete in HTTP story specs** — not left to dev model interpretation. Specify: seconds, retry count, backoff strategy, failure return type.
