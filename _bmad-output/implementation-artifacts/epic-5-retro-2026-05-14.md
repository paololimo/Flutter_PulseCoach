## What Went Well

### 1. Strong Layering and Architecture Discipline

The epic kept AI logic mostly pure and testable. `StateVector`, `BehavioralStateMachine`, `SafetyRules`, `BanditEngine`, and `ExplanationGenerator` are all structured around deterministic domain behavior. The isolate boundary in Story 5.5 gives the project a clear execution pattern for AI computation.

**Lesson:** Pure Dart AI components are easier to review, test, and harden than UI-coupled logic.

### 2. Review Workflow Caught Real Product Bugs

Story 5.5 review found several correctness issues before closure:

- Local date versus UTC skew in plan dates and generated timestamps
- Cold-start behavioral state not being persisted
- New-user `missedSessions` incorrectly derived as nonzero
- Non-transactional plan save behavior
- Missing exception handling around AI calls and BLoC handlers
- Missing isolate timeout handling
- Concurrent regeneration race

**Lesson:** The review process is not cosmetic. It prevented state drift, cache corruption, loading-state hangs, and user-visible incorrect metrics.

### 3. Previous Retro Commitments Mostly Carried Forward

Epic 4 committed to explicit required test scenarios, deferred item review, and integrating `getProfile()` caching into Story 5.1. Epic 5 story files show explicit test scenario blocks and systematic review/deferred tracking. Several Epic 5 stories also resolved earlier deferred work, especially around `BanditState` initialization, name collisions, RPE validation at construction/use-case boundaries, and behavioral state persistence.

**Lesson:** Retrospective action items are useful when they are embedded into story specs, not left as separate prose.

### 4. Test Coverage Expanded Across the Right Risk Areas

The suite now passes at 346 tests. Epic 5 added targeted coverage for:

- Domain model serialization and equality
- State machine transitions and safety constraints
- Safety rule boundary behavior
- Bandit reward calculation and selection
- AI isolate pipeline behavior
- Daily plan cache, persistence, regeneration, and BLoC state transitions
- Explanation generation branches and boundaries

**Lesson:** The highest-risk logic in this epic is covered closer to the domain layer, where tests are cheaper and more deterministic.

## What Did Not Go Well

### 1. Story 5.5 Was Too Dense

Story 5.5 combined isolate execution, StateVector assembly, plan persistence, cache-hit behavior, behavioral state persistence, graceful degradation, cold-start handling, regeneration, DI, BLoC wiring, and tests. The review findings show that too many correctness concerns were concentrated in one story.

**Impact:** A large number of critical patches were required at review. The story was completed, but the risk surface was larger than necessary.

**Lesson:** Pipeline orchestration stories should be split when they combine domain assembly, persistence semantics, concurrency, and presentation state.

### 2. Some Product Semantics Remain Unsettled

Deferred work still contains product-level behavior questions:

- `active + missedSessions >= 2` does not escalate directly to `atRisk`
- `recovering` has no demotion path for high RPE or missed sessions
- `atRisk -> recovering` can happen with two low RPE values without a streak or missed-session guard
- Explanations can be generic or identical across multiple sessions
- Step-count explanations ignore time of day

**Impact:** The implementation is spec-compliant, but some edge behavior may feel wrong once real users interact with the Today screen.

**Lesson:** Deterministic AI rules need product review as much as technical review.

### 3. Analyze Is Still Not Clean

`flutter analyze` reports 38 issues. Most are info-level lints, but several warnings are real cleanup items:

- Unused import in weather local data source
- Unused imports across tests
- Unused local variable in health data source tests

**Impact:** Passing tests are strong, but the project does not yet meet its own zero-warning quality rule.

**Lesson:** Analyze cleanup should be treated as closure work, not background noise.

### 4. End-to-End Product Validation Is Blocked by Placeholder UI

The `DailyPlanBloc` and use cases exist, but the visible Today screen is still a placeholder. Device verification reached the app shell and tabs, but plan generation cannot yet be validated through the normal user path.

**Impact:** Epic 5 is complete at the domain/use-case/BLoC level, but user-facing validation depends on Epic 7 wiring.

**Lesson:** A backend-heavy epic should explicitly record the gap between code completion and user-path validation.

## Next Epic Preview - Epic 6: Exercise Catalog

Epic 6 introduces ExerciseDB integration, a local exercise cache, a bundled fallback catalog, and a session browsing screen. It directly affects Epic 5 output because `BanditEngine` currently creates placeholder `PlannedSession` values:
