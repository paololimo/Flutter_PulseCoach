## What Went Well

### 1. Cleanest Execution Across All Epics

Zero blockers, zero build errors, zero debug sessions across all 3 stories. The dev agent followed specs faithfully with no implementation friction. This is the first epic with no debug log references in any story record.

**Lesson:** Spec maturity has reached a level where the dev agent can execute without getting stuck. The 'Defensive Requirements' section added after Epic 3 contributed to this.

### 2. Privacy by Design — First-Class Architecture Decision

City-level coordinates (`(coord * 10).round() / 10`, ~11km precision) are enforced at the `LocationService` boundary. `ACCESS_COARSE_LOCATION` only on Android. `NSLocationWhenInUseUsageDescription` on iOS. Raw GPS data never stored, never transmitted. The privacy constraint (NFR8, FR35) is enforced by architecture, not by convention.

**Lesson:** Privacy constraints enforced at the architecture boundary are more reliable than developer discipline.

### 3. Pattern Consolidation — Wrapper Injection, Transactional Cache, TTL Cache-First

Three mature, reusable patterns emerged:
- **GeolocatorWrapper** — same injection pattern as `HealthModule` from Epic 3. Wraps static methods for testability.
- **replaceCache() transactional DAO** — atomically delete + insert in transaction. Single-slot cache guaranteed.
- **TTL cache-first flow** — check cache → if valid return immediately → if stale/missing fetch from network → if network fails return stale.

**Lesson:** Pattern repetition across epics is a sign of architectural maturity. These patterns should be referenced in future story specs.

The Sonnet/Opus review workflow continues to be the highest-ROI quality practice. Without review, at least 2-3 bugs would have reached production.

### 5. Test Suite Growth — 24 Tests in 3 Stories

153 → 177 tests with comprehensive coverage: API parsing, repository TTL scenarios, location permission flows, DAO transactions, use case pass-through. Failure path testing commitment from Epic 2 respected in all stories.

## What Didn't Go Well

### 1. Review Finds Missing Tests in Every Story (3/3) — Systematic Pattern

| Story | Missing Tests Found by Review |
|---|---|
| 4.1 | CacheException path in WeatherRepositoryImpl |
| 4.2 | CacheException from getCachedWeather (read side) |
| 4.3 | denied → whileInUse permission grant flow (first-launch happy path) |

**Root cause:** The dev agent writes tests for scenarios explicitly in the Acceptance Criteria but does not spontaneously add tests for edge cases not mentioned in the spec. The 'Defensive Requirements' section covers production code edge cases but not test case enumeration.

**Action:** Add 'Required Test Scenarios' sub-block to story specs — enumerate minimum test cases explicitly. The dev agent will implement them all.

### 2. Geolocator Spike Commitment Not Honored

Epic 3 retro explicitly committed: "Spike geolocator on physical device before Story 4.3 creation." This was not done. No blockers resulted, but the commitment was broken.

**Root cause:** The commitment existed only as a line in the retro markdown document. It was not tracked as an actionable item in sprint-status.yaml with a blocking relationship to Story 4.3.

**Action:** All retro commitments that require action (spikes, preparatory tasks) must be added to sprint-status as trackable entries.

### 3. Deferred Items Growing — 39 Cumulative

From 13 (Epic 1) → 22 (Epic 2) → 28 (Epic 3) → 39 (Epic 4). +11 new in this epic.

**Analysis:** The growth rate varies (13, 9, 6, 11) but is not accelerating dangerously. Critically, most new deferred items are **pre-existing conditions documented during review**, not new regressions introduced by Epic 4 code. The review process is surfacing latent debt, not creating it.

**Key promotion:** `getProfile()` caching — open since Epic 1 (4 epics!) — promoted from Medium to **High** by Paolo. Rationale: Epic 5's `StateVector` reads `UserProfile` per AI generation cycle; with Dart Isolate (5.5), profile must be passed as parameter. Caching becomes an architectural prerequisite.

### 4. Cache Error Handling Took 2 Stories to Get Right

Story 4.1 treated cache write failure as a hard error (`Left(ServerFailure)`). Story 4.2 review found that this approach discards fresh data when the cache write fails — the fix restructured to build `WeatherContext` before cache write, making `CacheException` non-fatal.

**Root cause:** Story 4.1's scope was "fetch and cache"; the nuance of "what if fetch succeeds but cache fails" wasn't anticipated until Story 4.2's deeper TTL work.

**Lesson:** Multi-story features (fetch → cache → TTL) should have error handling edge cases reviewed holistically, not per-story.

## Key Insights

1. **Review finds missing tests systematically (3/3 stories)** — The fix is explicit 'Required Test Scenarios' in specs, not hoping the dev model adds them spontaneously.
2. **Deferred items are documentation of pre-existing debt, not degradation** — 39 cumulative, but growth reflects review thoroughness, not declining quality. Only `getProfile()` caching requires proactive action (promoted to High).
3. **Retro commitments must be tracked in sprint-status, not just in markdown** — The spike geolocator commitment was lost because it lacked tracking infrastructure. Process commitments need the same tracking rigor as stories.
4. **Privacy by design through architecture boundaries is more reliable than convention** — `LocationService` rounds before returning. No downstream code can accidentally leak precise GPS.
5. **Pattern consolidation is a maturity signal** — GeolocatorWrapper, replaceCache, TTL cache-first are now established precedents. Reference them in future specs.
