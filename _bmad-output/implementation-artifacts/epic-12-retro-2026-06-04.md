## What Went Well

1. **Spike-first de-risking paid off (12.1).** The epic was designed low-commitment — validate feasibility before committing to 12.2–12.4. The spike confirmed Wear round-screen rendering (454×454) before any phone-side work, and explicitly documented the compatibility caveat (`wear_plus 1.2.4` has no `WearApp`).
2. **`E11R-PREP` directly unblocked the epic.** The Epic 11 retro action item ("configure the WearOS environment before scheduling 12.1") was ✅ done — the `Wear_OS_Large_Round` AVD (created 2026-06-02) was used throughout. A prep item that paid off immediately, exactly as intended.
3. **On-device verification done AND documented.** The recurring "verification done but the record slips" failure mode (Epic 11) was closed: a full real end-to-end run plus a detailed `CLAUDE.md` note at the Epic 10 standard. Progression over Epic 9 (skipped) and Epic 11 (tablet gap + undocumented).
4. **Silent-degradation discipline (AC4) held across all stories.** Every `Wear`/`watch_connectivity` call is wrapped in try/catch; the phone session lifecycle is never affected by the watch. Treated as a best-effort side channel throughout.
5. **Adversarial code reviews caught real defects inline.** 12.4: the reconnect-poller re-flip bug (D2 — a dismissed-after-RPE watch could be flipped back to the summary) and the application-context-sync scope deviation (D1) were both caught and properly resolved/ratified with test coverage, not waved through.

## Challenges & Carry-Forward Risks

1. **`wear_plus 1.2.4` did NOT provide the messaging API the stories assumed (the headline issue).** The spike (12.1) found no `WearApp`. Then 12.2 **HALTED at Task 2 pre-flight** because `wear_plus` exposes no `getNodes()/sendMessage()/receiveMessages()`. This forced a **mid-story package change** to `watch_connectivity 0.2.8` (Project-Lead approved). The architecture and story Tasks were written against package capabilities that did not exist in the pinned version.
2. **The spike validated rendering but not transport.** The 12.1 outcome explicitly listed phone↔watch data transport as a *known gap* — and that is precisely where the risk detonated in 12.2. The spike scope did not cover the actually-risky path.
3. **Severe pairing/environment friction.** The 12.2 debug log is a saga: unauthenticated Play Store, non-installable companion APK, Cloudflare-blocked APK downloads, AppleScript/Accessibility permission gates. Resolved only when the Project Lead supplied a local companion APK. The API 26 phone is below the API 30 the official pairing assistant expects.
4. **Device reality diverged from spec (12.4).** `sendMessage` + `isReachable` alone did not deterministically recover the post-session summary after a watch-process restart → an unplanned **application-context sync** was needed, touching a file marked NO-CHANGES. Properly ratified (D1), but it shows on-device behavior outrunning the spec design.

**Theme:** the recurring failure mode this epic was *assuming a dependency/environment capability and only discovering the gap at real execution* — same spirit as the Epic 9 "widget tests at 800dp can't see a 360dp overflow" lesson. The fix is to push validation of the risky path earlier (spike scope + story-creation pre-flight).
