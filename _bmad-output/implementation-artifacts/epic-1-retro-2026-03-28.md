The review-patch workflow intercepted latent bugs before they became structural debt. Key examples:

**Lesson:** On a foundation epic, every review fix prevents multiplied debt in future epics.

## What Didn't Go Well

### 1. Version Conflicts in Flutter Ecosystem (Story 1.2)
- `wear_plus: ^2.0.2` specified in planning — v2.x does not exist on pub.dev
- `drift_flutter` required `^0.3.0` for compatibility with `drift ^2.32.0`
- `freezed` 3.x required for compatibility with drift_dev >=2.28.2
- `bloc_test` required `^10.0.0` for bloc ^9.x compatibility

**Root cause:** Spec versions written during planning became stale before implementation.
**Action:** Verify versions on pub.dev at implementation time, not from spec.

### 2. Naming Collisions (Stories 1.1, 1.4)
- `date_utils.dart` shadowed Flutter's built-in `DateUtils` → renamed to `pulse_date_utils.dart`
- `@DataClassName('RpeFeedback')` collided with table class `RpeFeedback` → renamed to `RpeFeedbackData`

**Root cause:** Silent collisions — code compiles but behavior is wrong.
**Action:** Check any name resembling a Flutter/Dart standard class; prefix selectively when collision exists.

### 3. Build_runner Expectations Inaccurate (Story 1.6)
- Task 9 in Story 1.6 stated "build_runner NOT required"
- Reality: `@injectable` on `ThemeCubit` required regeneration of `injection.config.dart`

**Root cause:** Incomplete understanding of when build_runner triggers.
**Action:** Simple rule — any new `@injectable`, `@singleton`, `@lazySingleton`, `@freezed`, or Drift table annotation = build_runner run, always.

### 4. Third-Party API Behavior Surprises
- `dartz` 0.10.1 already defines `isLeft()`/`isRight()` as instance methods — extension getters with same names were shadowed
- `getIt.isReady` is a method (not property) in GetIt 8.x

**Root cause:** Documentation doesn't always reflect runtime behavior.
**Action:** Verify API behavior with actual code, not just docs.

## Significant Discoveries

### Schema Gap: `disclaimerAccepted` field missing from `UserProfile`

**Discovery:** Epic 2 Story 2.1 requires persisting medical disclaimer acceptance. The `user_profile` table has no `disclaimerAccepted` field. Additionally, the disclaimer is accepted **before** the profile is fully set up (Story 2.3), creating a sequence challenge.

**Decision:** Use partial `UserProfile` row approach:
- Story 2.1 inserts row with `disclaimerAccepted: true`, `onboardingCompleted: false`, all other fields nullable/default
- Story 2.3 updates the same row with full profile data
- Redirect logic changes from `profile != null` to `profile != null && profile.onboardingCompleted == true`

**Impact:** Requires schemaVersion 2 migration as prep task before Epic 2.

### Redirect Logic Semantically Incorrect

**Discovery:** Current redirect uses `getProfile() != null` as proxy for "onboarding completed". This was always imprecise — a profile row can exist without onboarding being complete (e.g., after disclaimer acceptance).

**Decision:** Fix redirect to `profile != null && profile.onboardingCompleted == true`. Add as explicit AC in Story 2.1 with 4 test scenarios:
1. No profile → redirect to disclaimer
2. Profile with `disclaimerAccepted: false` → redirect to disclaimer
3. Profile with `disclaimerAccepted: true`, `onboardingCompleted: false` → redirect to onboarding
4. Profile with `onboardingCompleted: true` → redirect to `/today`
